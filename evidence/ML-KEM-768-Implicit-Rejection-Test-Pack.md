# ML-KEM-768 Implicit-Rejection Test Pack

Behavioral test pack for ML-KEM-768 decapsulation implicit rejection,
checked against NIST FIPS 203. This file is the single evidence pack:
it records the implementation under test, the exact execution command,
the primary-source requirements, the results table and the unedited output
of the measured run.

Repository: https://github.com/araupooo/mlkem-768-implicit-rejection-test-pack

## 1. Implementation under test

- **Library:** pyca/cryptography **50.0.2** (pinned in `requirements.txt`),
  released 2026-09-30 on PyPI. Source: https://github.com/pyca/cryptography
- **API:** `cryptography.hazmat.primitives.asymmetric.mlkem`
  (`MLKEM768PrivateKey.generate()`, `.public_key()`, `.encapsulate()`,
  `.decapsulate()`). The ML-KEM API was added in cryptography 47.0.0.
  API documentation: https://cryptography.io/en/latest/hazmat/primitives/asymmetric/mlkem/
- **Cryptographic backend:** OpenSSL (the wheel's bundled OpenSSL;
  the measured run printed `OpenSSL 4.0.3 29 Sep 2026`).
- **Runtime environment of the measured run:** GitHub Actions runner
  `ubuntu-24.04`, Python 3.12.16 (CPython),
  platform `Linux-7.0.0-1017-azure-x86_64-with-glibc2.39`.
  Workflow: `.github/workflows/run-harness.yml`.

## 3. Requirements taken from the primary source (verbatim)

Source: NIST FIPS 203, "Module-Lattice-Based Key-Encapsulation Mechanism
Standard", August 2024, DOI 10.6028/NIST.FIPS.203,
https://doi.org/10.6028/NIST.FIPS.203
(https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.203.pdf).
Page numbers are the printed page numbers of the standard.

### 3.1 Implicit rejection — Section 6.3, page 33

> "The decapsulation algorithm then re-encrypts m' and computes a candidate
> shared secret key K' in the same manner as should have been done in
> encapsulation. Specifically, K' and the encryption randomness r' are
> computed by hashing m' and the encryption key of K-PKE, and a ciphertext
> c' is generated by encrypting m' using randomness r'. Finally,
> decapsulation checks whether the resulting ciphertext c' matches the
> provided ciphertext c. If it does not, the algorithm performs an
> "implicit rejection": the value of K' is changed to a hash of c together
> with the random value z stored in the ML-KEM secret key (see the
> discussion of decapsulation failures in Section 3.2). In either case,
> decapsulation outputs the resulting shared secret key K'."

Algorithm 18 ML-KEM.Decaps_internal(dk, c), Section 6.3, page 33:

> "4: z ← dk[768k+64 : 768k+96] ▷ extract implicit rejection value"
> "7: K̄ ← J(z ‖ c)"
> "9: if c ≠ c' then"
> "10: K' ← K̄ ▷ if ciphertexts do not match, "implicitly reject""

> "The "implicit reject" flag computed in step 9 (by comparing c and c') is
> a secret piece of intermediate data. As specified in the requirements in
> Section 3.3, this flag shall be destroyed prior to
> ML-KEM.Decaps_internal terminating. In particular, returning the value of
> the flag as an output in any form is not permitted."

### 3.2 Ciphertext checking — Section 7.3, page 37

Decapsulation input check:

> "1. (Ciphertext type check) If c̃ is not a byte array of length
> 32(d_u·k + d_v) for the values of d_u, d_v, and k specified by the
> relevant parameter set, then input checking has failed."

> "Ciphertext checking shall be performed with every execution of
> ML-KEM.Decaps."

### 3.3 Decapsulation failures — Section 3.2, page 14

> "Decapsulation failures. Provided that all inputs are well-formed and
> randomness generation is successful, the key establishment procedure of
> ML-KEM will never explicitly fail, meaning that both ML-KEM.Encaps and
> ML-KEM.Decaps will each output a 256-bit value."

### 3.4 ML-KEM-768 parameters — Section 8, Tables 2 and 3, page 39

ML-KEM-768: n = 256, q = 3329, k = 3, η1 = 2, η2 = 2, d_u = 10, d_v = 4.
Sizes: encapsulation key 1184 bytes, decapsulation key 2400 bytes,
ciphertext 1088 bytes, shared secret key 32 bytes.

## 4. Harness

File: `harness/mlkem_implicit_rejection.py` (187 lines). It uses only the
public API of the implementation under test; it does not implement any
ML-KEM algorithm itself.

For each of 25 fresh key pairs it checks:

1. **Valid shared-secret agreement** — `encapsulate()` followed by
   `decapsulate()` of the unmodified ciphertext returns the same 32-byte
   shared secret.
2. **Modified-ciphertext rejection** — decapsulating a ciphertext with one
   flipped byte (byte 0, and byte 1087, the last byte) returns a value
   that differs from the valid shared secret (Section 6.3 implicit
   rejection).
3. **Repeated-decapsulation determinism** — decapsulating the same modified
   ciphertext three times returns the same value every time.
4. **Second distinct modification** — a ciphertext modified at a different
   byte position (byte 544) yields a value that differs from the valid
   shared secret and from the first modification's value.
5. **Sizes** — encapsulation key 1184 bytes, ciphertext 1088 bytes,
   shared secret 32 bytes (Section 8, Table 3). The private key is
   serialized by this library as the 64-byte seed (d ‖ z) of Section 7.1,
   from which the 2400-byte decapsulation key is derived internally; the
   2400-byte expanded form is not exposed by the library's API.
6. **Ciphertext type check** — decapsulation of a wrong-length ciphertext
   (1087 and 1089 bytes) is refused with `ValueError` (Section 7.3).

Comparison evidence is reported as SHA-256 digests of the 32-byte outputs,
so equality and difference are shown without printing the secrets.

## 7. Compliance limitations

These are behavioral checks on this one implementation. They show that the
implementation rejects modified ciphertexts by returning a different,
deterministic value, as FIPS 203 Section 6.3 requires, and that valid
encapsulation and decapsulation agree. They do not prove full standards
compliance: they do not run NIST known-answer tests (NIST CAVP / ACVP
ML-KEM test vectors), do not verify the internal re-encryption comparison,
and do not test side-channel or constant-time properties.
